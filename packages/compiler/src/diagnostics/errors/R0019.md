# R0019: extern symbol not found

The library an extern binds to does not export its C symbol. Without this check the
program would build and then abort at launch, when dyld fails to bind the symbol. The
error is at the extern. A bare `extern fn` binds to libSystem, so it is checked
against libSystem (libc, libm and the rest of what libSystem re-exports).

Only the externs the program calls are checked. An extern called only in a `when` arm
that is not taken, or never called, is not imported, so it does not need to exist on
this target. A call in any other dead code counts, such as an `if false` branch or a fn
nothing calls, so the error does not depend on the opt level. `toy check` reports it as
`build` does.

```
import std/ffi

extern "z" {
    fn crc_32(crc: int, s: cstr, n: int) -> int   // error: C symbol 'crc_32' is not
}                                                 // exported by library 'z'
extern fn putz(s: cstr) -> int32   // error: C symbol 'putz' is not exported by libSystem

fn main() -> int {
    s := "hi".to_cstr()
    unsafe { crc_32(0, s, 2) + putz(s).into() }
}
```

A library on disk is checked through its export trie, including the libraries it
re-exports, which are found as dyld finds them: `@loader_path/` from the re-exporting
library's folder, `@rpath/` through its LC_RPATHs and then that folder. A system
library in the dyld shared cache is checked through dyld. A re-exported library toy
cannot locate (an `@executable_path/` name, say) is trusted.

Fixes:

- Check the spelling against the library's header, or list its exports with
  `nm -gU libfoo.dylib` (each name has a leading `_`).
- Put the extern in the block of the library that defines it.
- A C macro or an inline function has no symbol; call what it expands to.
