# T0082: a runtime fn can reach a GC allocation

The modules under `core/rt/` are the runtime: the fns the compiler's lowered code calls,
such as `str_eq` in `core/rt/str`. A call to one of them must never let the collector run,
so the backend can keep references in registers across it. So no fn in `core/rt/` may
reach a GC allocation, directly or through the fns it calls.

The compiler checks this after type checking by walking the call graph from every
`core/rt` fn. The error names the fn and the shortest call path to the allocation:

```
// core/rt/probe.toy
import std/vec

pub fn first_len(s: str) -> int {   // error: core/rt fn 'first_len' can reach a GC allocation:
    return helper(s)                //   first_len -> core/rt/probe.helper -> std/vec.Vec.new$str
}                                   //   -> core/mem.ga_new$str -> gc_alloc

fn helper(s: str) -> int {
    xs := Vec[str].new()
    xs.push(s)
    return xs.len()
}
```

A callee shows as its symbol, the name a backtrace prints: a generic instance carries its
type arguments after a `$`. The error points at the fn, and its second label at the first
call on the path. `helper` gets an error of its own, since it is a `core/rt` fn too.

The walk counts as an allocation anything that may allocate and anything whose target it
cannot see:

- `gc_alloc`, `gc_collect`, `ref_new`, the descriptor calls `call_hash` and `call_eq`, and
  a call of a builtin it does not know;
- a str `concat`, `to_string`, a list literal, a closure, a boxed local and a method
  bound as a value;
- a call through a fn value, a protocol method, a derived witness over a field that is
  itself a struct or enum, a `?` and a `for`-in loop, since each runs code it does not
  follow.

An operator is followed as it lowers. On a number, a `bool`, a `str`, a `Ref` or a fn
value it is inline (a `str ==` calls `core/rt` `str_eq`, which the rule checks too). On a
struct or enum, `char` among them, it calls the type's `Eq`, `Ord` or arithmetic witness,
and the walk goes into it. A derived `Eq`, `Ord` or `Hash` whose fields all compare inline
allocates nothing.

A call of a C function does not allocate. A toy fn named as a value counts as called,
since C may call it back.

Fixes:

- Take the value the fn would build as a parameter, so the caller allocates it.
- Call the fn that does the work directly instead of through a fn value, a protocol or
  an operator.
- Move the code that allocates out of `core/rt` into the `core` or `std` module that
  uses it.

The rule applies only to `core/rt`, which ships with the compiler; a program cannot add a
module there. A dev build that tests the rule puts one on disk with `--dev-core-imports`.
